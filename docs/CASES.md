# Разбор публичных атак на агентов

Для каждого кейса: что произошло, как устроена атака, что от неё остаётся в журнале сессии и что `seance` с этим делает. Главный вопрос здесь не «умеет ли инструмент всё», а **где проходит граница того, что видно по журналу**. Тексты атак в `tests/corpus/scenarios.py` (набор `public`) написаны мной по описаниям исследователей, не дословно, домены в зоне `.test`. Факты взяты из источников ниже; где источники расходятся, это отмечено.

## 1. GitHub MCP: «токсичный поток» (май 2025)

**Что произошло.** [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability) показали, что злоумышленник может завести issue в публичном репозитории жертвы. Когда агент жертвы читает issues через официальный сервер GitHub MCP, текст issue подбивает его прочитать приватные репозитории и выложить сведения о них в публичный pull request. Ошибки в самом сервере нет: [heise](https://heise.de/-10400040) подчёркивает, что это prompt injection, а доступ к приватным данным агент получает потому, что сервер работает от имени пользователя. Invariant считает проблему архитектурной и не лечащейся патчем сервера; Саймон Уиллисон описывает такой набор как «смертельную тройку»: доступ к приватным данным, недоверенный текст и способ вынести данные.

**В журнале:** результат `list_issues`, затем чтения файлов приватного репозитория через MCP, затем `create_pull_request`.

**Что делает seance.** Вызов `create_pull_request` считается опасным действием («запись во внешний сервис через MCP»). Но связь строится по признакам инструкции, а текст такого issue написан как просьба («добавьте раздел об авторе, это очень важно»), без «игнорируй прежние указания». **Сценарий `p_github_mcp_toxic_flow` не обнаруживается, и это проверяется тестом.** Чтобы такое ловить, нужна политика, а не поиск слов: «агент, читавший публичный issue, не должен писать в публичные репозитории и читать приватные в том же ходе». Это работа для шлюза (см. проект citadel из того же портфеля), а не для разбора журнала.

## 2. Supabase MCP + Cursor (июль 2025)

**Что произошло.** По описанию [Pomerium](https://www.pomerium.com/blog/when-ai-has-root-lessons-from-the-supabase-mcp-data-leak) и [Саймона Уиллисона](https://simonwillison.net/2025/Jul/6/) тикет поддержки содержал инструкцию. Когда разработчик просматривал тикеты через Cursor, агент читал таблицу с токенами интеграций и записывал результат обратно в тикет, который видит автор. Причина в привилегиях: агент работал с ключом `service_role`, обходящим политики строк. Supabase добавил режим только для чтения и ограничение по проекту, а сам prompt injection оставил главным риском.

**В журнале:** тикет в результате SQL-запроса, запрос к таблице токенов, запрос на запись.

**Что делает seance.** Запрос к таблице с названием `token`, `secret`, `credential`, `password` через MCP считается чтением секретов, запись через `execute_sql` с `insert/update/delete` считается записью. Связь устанавливается, если в тикете есть обращение к ассистенту («instructions for the assistant») или «не говори пользователю». `p_supabase_support_ticket` ловится. Если автор атаки пишет мягче, пропуск.

## 3. Amazon Q Developer (июль 2025)

**Что произошло.** По данным [CyberInsider](https://cyberinsider.com/amazons-ai-coding-assistant-for-vsc-infected-with-data-wiper/) и [The Register](https://www.theregister.com/2025/07/24/amazon_q_ai_prompt/), в версию 1.84.0 расширения для VS Code попал промпт, который велел ИИ стирать локальные данные и удалять облачные ресурсы. Компания AWS объясняет это слишком широкими правами токена GitHub в системе сборки. Выпущена версия 1.85.0. AWS утверждает, что ошибка в синтаксисе помешала исполнению и клиентские ресурсы не пострадали. Источники расходятся в деталях (в конфиге промпт или в скрипте упаковки).

**В журнале:** только команды агента. Текст, который к ним привёл, находится внутри самого инструмента и в журнал не попадает.

**Что делает seance.** Сами команды (`aws s3 rm --recursive --force`, `terminate-instances`) распознаются как «удаление облачных ресурсов», но без недоверенного текста перед ними связи нет, и по умолчанию такая находка не показывается. **Граница:** инструмент разбирает то, что попало в журнал; подмену самого агента или его системного промпта он не видит. Защита здесь в цепочке поставки: пиннинг версий, проверка релизов, права токенов сборки.

## 4. Rules File Backdoor (март 2025)

**Что произошло.** [Pillar Security](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents) показали, что невидимые символы Unicode в файле правил (`.cursorrules`, инструкции Copilot) подмешивают скрытые указания ко всем будущим сессиям команды. В демонстрации сгенерированный HTML содержал скрипт, отправляющий данные на внешний сервер. По сообщению [The Hacker News](https://thehackernews.com/2025/03/new-rules-file-backdoor-attack-lets.html), Cursor и GitHub сочли ответственность пользовательской; позднее GitHub стал показывать предупреждение о скрытом Unicode на github.com.

**В журнале:** файл правил приходит как контекст или результат чтения, и скрытый текст лежит в нём как обычные символы.

**Что делает seance.** Это единственный случай, где защита чисто «детекторная». Невидимый текст длиной от 8 символов (теги U+E0000, bidi-управляющие) ищется **во всём, что агент прочитал**, включая файлы правил и контекст клиента, и показывается расшифрованным. Короткие последовательности (флаги-эмодзи) не срабатывают. `p_rules_file_backdoor` ловится, обычный файл с флагом нет.

## 5. GitHub Copilot, CVE-2025-53773 (2025)

**Что произошло.** [Исследование Йоханна Рехбергера](https://embracethered.com/blog/posts/2025/github-copilot-remote-code-execution-via-prompt-injection): инструкция в тексте, который читает Copilot (файл, страница, issue), заставляет агента дописать в настройки редактора автоподтверждение инструментов, то есть «режим YOLO», после чего команды выполняются без вопросов. Исправлено в августе 2025. Один из источников утверждает, что та же схема работает на более новой настройке; это заявление вендора, подтверждения CVE нет.

**В журнале:** текст страницы и правка `settings.json`.

**Что делает seance.** Правка `.vscode/settings.json`, `.claude/`, `.cursor/`, `.mcp.json` считается правкой конфигурации агента. Если путь назван недоверенным текстом, а пользователем нет, связь «по пути» средняя, а с инструкцией внутри текста сильнее. Ловится.

## 6. Nx «s1ngularity» (август 2025)

**Что произошло.** По [Socket](https://socket.dev/blog/nx-packages-compromised) и [Wiz](https://www.wiz.io/blog/s1ngularity-supply-chain-attack) вредоносные версии пакетов Nx запускали установленные на машине ИИ-CLI (Claude, Gemini, Amazon Q) без подтверждений (`--dangerously-skip-permissions`, `--yolo`, `--trust-all-tools`) и просили искать секреты и пути к кошелькам. Данные уходили в публичный репозиторий на GitHub жертвы через её `gh`. Orca называет это первой цепочкой поставки, использующей локальные ИИ-инструменты.

**В журнале порождённой сессии:** первое «сообщение пользователя» является атакующим промптом, дальше обычные команды `find` и `cat ~/.npmrc`. Для `seance` это действия, о которых «попросил пользователь».

**Что делает seance.** **Не видит**: недоверенного текста нет, есть слова пользователя. Можно ловить только прямой запуск другого агента без подтверждений командой в журнале (`agent-spawn`): `p_agent_spawn_flags` ловится, когда это происходит после недоверенного текста. Эта граница общая для всех атак, где вредонос играет роль пользователя. Нужна защита на уровне установки пакетов и запрета неинтерактивных запусков.

## 7. postmark-mcp (сентябрь 2025)

**Что произошло.** [Koi Security](https://www.koi.ai/blog/postmark-mcp-npm-malicious-backdoor-email-theft) нашли поддельный пакет MCP-сервера: версия 1.0.16 добавила скрытую копию (BCC) каждого письма на сторонний адрес. «Первый в мире» — формулировка самих исследователей, независимо я её не проверил. Оценки масштаба расходятся (от тысяч писем в день из около 300 организаций до чуть более полутора тысяч загрузок). ActiveCampaign, владелец Postmark, заявила, что к пакету отношения не имеет.

**В журнале:** обычный вызов `send_email` и ответ «отправлено». Подмена происходит внутри сервера.

**Что делает seance.** **Ничего, и не может.** Атака не про недоверенный текст и не про действия агента. Здесь помогают другие инструменты портфеля: basilisk закрепляет определения инструментов и ловит подмену (`pin`/`verify`), citadel ставит между агентом и сервером шлюз. Но и они не видят, что делает код сервера внутри. Против этого защищает только проверка пакета.

## 8. CurXecute и MCPoison (Cursor, август 2025)

**Что произошло.** По [Tenable](https://www.tenable.com/blog/faq-cve-2025-54135-cve-2025-54136-vulnerabilities-in-cursor-curxecute-mcpoison): в CVE-2025-54135 (CurXecute) создание файла конфигурации MCP не требовало подтверждения, и prompt injection мог добавить туда запуск команды. В CVE-2025-54136 (MCPoison) конфигурацию можно было подменить уже после того, как пользователь её одобрил. Исправления вышли в версиях 1.3 и 1.3.9. Оценки опасности по источникам расходятся (от 7.2 до 8.8 и 8.5-9.8). Названия CurXecute и MCPoison не значатся в NVD, по ним нельзя искать записи.

**В журнале:** внешнее сообщение, затем создание или правка файла `mcp.json`.

**Что делает seance.** Правка `.cursor/mcp.json` или `.mcp.json` после недоверенного текста с инструкцией ловится (`p_curxecute_mcp_json`). MCPoison, где конфигурацию подменяют вне сессии (например, `git pull`), в журнале агента не видна.

## 9. EchoLeak (Microsoft 365 Copilot, июнь 2025)

**Что произошло.** [Aim Labs](https://thehackernews.com/2025/06/zero-click-ai-vulnerability-exposes.html) нашли в Microsoft 365 Copilot критическую уязвимость CVE-2025-32711 (CVSS 9.3): внешнее письмо с подготовленным текстом позволяло без действий пользователя вынести данные из его сессии. Microsoft исправила проблему на стороне сервера, клиенту ничего делать не нужно. Один источник сообщает об эксплуатации, остальные нет, я бы этому утверждению не доверял.

**В журнале (аналог для агента на ноутбуке):** письмо через MCP-почту, затем запрос на адрес с данными в параметрах.

**Что делает seance.** Для самого Copilot журналов нет. Для агентов с похожей схемой: запрос с длинными данными в адресе после письма с обращением к ассистенту ловится (`p_echoleak_style`). Вынос через отображение картинки или ссылки в интерфейсе в журнале не виден.

## 10. Cursor CVE-2026-22708 (январь 2026)

**Что произошло.** По [Pillar Security](https://pillar.security/blog/the-agent-security-paradox-when-trusted-commands-in-cursor-become-attack-vectors) и [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-22708/): встроенные команды оболочки (`export`, `typeset`) выполнялись в режиме автозапуска без одобрения. Атакующий через prompt injection задавал переменную окружения вроде `PAGER`, и уже разрешённая команда (`git branch`) запускала чужую программу. Исправлено в версии 2.3. Оценка опасности по источникам расходится (7.2 или 9.8).

**В журнале:** `export PAGER=...; git branch` или та же переменная в начале команды.

**Что делает seance.** Подмена `PAGER`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `BASH_ENV`, `NODE_OPTIONS`, `PYTHONSTARTUP` считается опасным действием. Добавление в `PATH` нет. `p_cursor_pager_env` ловится.

## Что из этого следует

1. **Журнал отвечает на вопрос «откуда это взялось», когда источник был текстом в сессии.** Атаки через сам инструмент (Amazon Q), через пакет (postmark-mcp), через слова «пользователя» (s1ngularity) в журнале следов не оставляют или оставляют неотличимые от обычных.
2. **Поиск слов в тексте не заменяет политику.** Самый известный кейс (GitHub MCP) написан как вежливая просьба, и разбор по ключевым фразам его не видит. Ловить такое должен шлюз по правилам доступа.
3. **Скрытый текст лучше всего детектируется отдельно от всего остального**, потому что у него нет легитимных применений в файлах правил.
4. **Оценка здесь оптимистична по построению.** Правила `mcp-write`, `env-poison`, `agent-spawn` и обращение к ассистенту по имени я добавил после чтения этих кейсов, а потом проверил на сценариях, которые сам же написал по тем же описаниям. Результат «7 из 7» это проверка, что правила делают то, что задумано, а не оценка на чужих данных.
